# 시세 수집·복구 개선 계획서

작성일: 2026-09-16
대상: KODEX 코스닥150(229200) 모의 전략 kr-etf-range-v0.2
상태: 계획 작성 완료. 이 문서 작성으로 코드·서버 설정을 변경하지 않는다.

## 1. 목표와 결론

최초 실행 시 최근 30분의 유효한 시세를 확보하고, 이후에는 시간을 따라 이동하는 최근 30분 데이터를 계속 갱신한다. 매매가 끝날 때마다 새로 30분을 기다리지 않는다.

짧은 연결 단절이나 프로세스 재시작 때문에 유효한 데이터를 전부 잃는 문제를 우선 해결한다. 다만 실제로 관측하지 못한 구간을 정상 데이터처럼 취급해서 대기를 줄이지 않는다. 주문·취소·잔고 대조와 손실 제한은 유지한다.

**핵심 제약:** 데이터를 보존하는 것만으로 모든 대기가 사라지지는 않는다. 현행 전략은 최근 30분 안에 10초 초과 수신 공백이 있으면 진입하지 않는다. 해당 공백의 신뢰할 수 있는 원자료를 복원하지 못하면 공백이 창에서 빠질 때까지 기다려야 한다. 이 기준 변경은 복구 버그 수정과 별개인 전략 변경으로 검증한다.

## 2. 확인된 현상과 아직 확인하지 못한 원인

사용자가 전달한 9월 16일 보고서:

- 모의 실현손익 약 -11.79원, 보유·미체결 0, 진입 구간 수 8. 구간 수는 체결 횟수가 아니다.
- 실행·주문 허용 상태는 정상이나, 최근 판단 사유가 `warming_30m`이다.
- 준비 표본 719개, 최신 호가 수신 경과 130ms. 최신 호가는 들어오지만 과거 창은 준비 부족이다.
- REST 조회의 HTTP 500과 이후 정상 대조 기록이 있다.

이 정보만으로 연결 종료, 수신 공백, 프로세스 재시작 중 무엇이 초기화를 일으켰는지는 확정할 수 없다. REST HTTP 500이 WebSocket 단절을 일으켰다고 단정하지 않는다. 현재 직접 서버 접속에 필요한 SSH 키가 없어, 원인 확인에는 접속 복구 또는 서버 진단 자료가 필요하다.

## 3. 코드에서 확인한 문제

| 위치 | 현재 동작 | 개선 필요 사항 |
|---|---|---|
| `src/lib/range/engine.ts`의 `quote()` | 표본 간격 10초 초과 또는 날짜 변경 시 배열 삭제 | 날짜 변경과 수신 공백을 구분하고, 같은 날 유효 표본은 보존 |
| 같은 파일의 `disconnect()` | 표본·최신 호가·체결 시각을 모두 초기화 | 과거 표본 보존과 현재 시세 무효화를 분리 |
| `src/lib/range/strategy.ts`의 `makeBox()` | 개수·기간·공백 부족을 모두 `warming_30m`으로 표시 | 최초 준비, 공백, 표본 부족을 별도 사유로 표시 |
| `scripts/range-runner.ts` | 재접속 판단과 REST 대조가 같은 루프에 있고 재접속 간격 제한은 60초 | REST 지연과 시세 연결 복구를 분리하고 연결 상태별 재시도 관리 |
| `src/lib/range/broker.ts` | close/error/파싱 오류를 구분하지 않고 종료 콜백 호출 | 종료 원인·구독 응답·파싱 실패를 구조적으로 기록 |
| `src/lib/range/store.ts` 및 실행기 | 시세는 SQLite에 있지만 시작 시 메모리 창에 복원하지 않음 | 최근 동일 세션의 검증된 표본만 복원 |
| 보고 화면 | `running`, 주문 활성 여부, 표본 수 위주 | 실제 진입 가능 여부·대기 원인·재평가 조건 표시 |

현행 준비 기준은 최근 30분 표본 1,620개 이상, 첫·마지막 표본 간격 1,790초 이상, 내부 최대 간격 10초 이하다. 최근 5분에도 270개 이상이 필요하다. 최신 호가·체결의 신선도와 추세·폭·비용 조건도 별도로 충족해야 한다.

## 4. 구현 계획

### 1단계 — 진단 가능하게 만들기

- 연결 시작·성공·종료, 구독 성공·실패, 재접속 시도·결과, 파싱 실패, 수신 공백, 데이터 복원 결과를 기록한다.
- 각 이벤트에 시각, 연결 세대 ID, 마지막 정상 호가·체결 수신 시각, 공백 길이, 표본 수, 안전한 오류 코드를 남긴다. 키·토큰·원문 인증 메시지는 기록하지 않는다.
- REST 오류는 엔드포인트 종류·HTTP 상태·증권사 오류 코드·지연을 별도로 기록한다. 주문 원문이나 계좌번호는 제외한다.
- 연결 종료와 파싱 오류의 중복 콜백으로 동일 장애를 중복 집계하지 않는다.
- 9월 16일 원장의 주문·체결·청산 기록을 추출해 실제 거래 횟수, 가격, 종료 사유를 확인한다. 요약 손익만으로 거래 경로를 추정하지 않는다.

### 2단계 — 데이터 보존과 복원

- 연결이 끊어져도 동일 거래일의 최근 30분 표본은 유지한다. 시간이 지난 표본만 제거한다.
- 연결 단절 즉시 최신 시세를 신규 주문에 사용할 수 없도록 표시한다. 과거 표본 보존은 주문 허용을 의미하지 않는다.
- 수신 공백은 별도 구간으로 기록한다. 종목·날짜·순서·중복·가격 격자·호가 역전·시각 유효성을 확인한다.
- 재시작 시 SQLite에서 동일 종목·거래일·세션의 최근 30분 표본을 정렬해 복원한다. 복원 완료 후에도 새 호가·체결 수신과 계좌 대조를 확인해야 진입을 허용한다.
- 기존 저장 시각은 수신 시각이다. 향후 공급자 시각과 수신 시각을 구분해 저장하며, 기존 데이터에 없는 정밀도를 만들어내지 않는다. 스키마 변경은 기존 원장을 보존하는 마이그레이션으로 한다.
- 자정·다음 거래일에는 이전 날 시세를 준비 표본으로 사용하지 않는다. 서버가 꺼져 있던 시간은 관측 공백으로 남긴다.
- 호가가 변하지 않았다는 이유로 누락 초를 임의 채우지 않는다. 데이터 보간, 이전 가격 복제, 분봉을 초별 호가로 변환하는 보충은 금지한다.

### 3단계 — 재접속과 진입 재개

- 연결 관리를 REST 조회 루프와 분리한다. 기존 REST 직렬 처리·호출 제한과 주문 중복 방지는 유지한다.
- 재접속 대기 초기안은 1·2·5·10·30초와 작은 무작위 지연이다. 구현 전 공급자 접속·구독 제한을 확인해 조정하고, 인증키 발급은 재접속마다 무조건 반복하지 않는다.
- 하나의 활성 연결만 유지한다. 이전 연결에서 늦게 도착한 close/error가 새 연결을 무효화하지 않도록 세대 ID로 검증한다.
- 신규 진입은 연결·구독 정상, 최신 호가·체결, 최근 30분/5분 데이터 품질, 주문·잔고 대조, 전략 조건을 모두 통과해야 재개한다.
- 10초 이하의 짧은 공백은 기존 창이 다른 품질 조건도 충족하면 전체 재수집 없이 재개한다. 임계값과 표본 개수 조건을 함께 적용한다.
- 10초 초과의 실제 공백은 보존된 창에서도 진입을 차단한다. 승인된 동일 의미·해상도의 원자료로 복구되거나 공백이 창에서 빠진 뒤 품질을 재평가한다.
- 보유 중 단절에서는 현행 미체결 취소·보유 청산 절차를 유지한다. REST 장애로 결과가 불명확하면 성공 처리하거나 주문을 무조건 재전송하지 않는다.
- A/B 가상 비교에도 동일한 데이터 품질 판정을 적용한다. 가상 포지션의 공백 중 체결·손절을 관측한 것으로 계산하지 않고 불확실한 구간을 표시한다.

### 4단계 — 상태 화면 개선

프로세스 실행, 주문 설정, 지금 진입할 수 있는 상태를 분리한다. 최소 다음 상태와 사유를 표시한다.

| 상태 | 의미 |
|---|---|
| 최초 시세 준비 | 아직 최초 30분 창을 확보하지 못함 |
| 연결 복구 중 | 연결 또는 구독이 정상화되지 않음 |
| 데이터 품질 대기 | 연결은 정상이지만 공백·표본 부족으로 진입 불가 |
| 전략 조건 대기 | 데이터는 준비됐지만 매수 조건 불충족 |
| 주문·포지션 관리 중 | 미체결 또는 보유를 관리 중 |
| 오류 중단 / 장 종료 | 자동 진입을 중단한 이유가 있음 |

최근 30분/5분 표본 수·커버리지·최대 공백, 마지막 정상 수신, 재접속 횟수, 현재 진입 차단 사유를 표시한다. 준비 완료 예상 시각은 추가 단절이 없다는 조건부 값으로 제공하고, 불명확하면 예상 불가로 표시한다. `warming_30m` 누적 횟수를 대기한 분 수로 해석하지 않도록 한다.

## 5. 과거 데이터 보충의 적용 범위

SQLite에 이미 저장된 표본의 복원은 우선 구현한다. 서버나 연결이 실제로 관측하지 못한 과거 호가는 DB에 없으므로 복원할 수 없다.

증권사 과거 조회 API가 동일한 호가·잔량·시각 해상도를 제공하는지는 별도 조사한다. 분봉·체결가가 있다는 사실만으로 현재 전략이 쓰는 호가 중간값과 잔량을 복구할 수 있다고 보지 않는다. 적합한 원자료가 없다면 REST 보충 기능을 억지로 추가하지 않는다.

긴 공백에서도 매매를 계속하려면 공백 허용 범위나 지표를 변경하는 별도 전략 실험이 필요하다. 1차 개선에서는 기존 10초 기준과 30분/5분 창을 완화하지 않는다.

## 6. 검증과 완료 기준

자동 테스트:

1. 정상 수집 중 매매 종료만으로 표본이 초기화되지 않는다.
2. 정상 30분 창에서 짧은 단절 후 복구하면 과거 표본이 유지되고, 품질 충족 시 다음 판단에서 재개한다.
3. 10초 경계·초과 공백·연속 짧은 공백으로 인한 커버리지 부족을 각각 검증한다.
4. 10초 초과 공백은 표본을 보존해도 진입하지 않으며, 충분한 새 데이터가 생기면 자동 해소한다.
5. 재시작 복원은 정렬·중복 제거·거래일 필터를 적용하고, 새 실시간 수신 전에는 주문하지 않는다.
6. REST HTTP 500만 발생했을 때 정상 시세 창을 삭제하지 않는다. 계좌 대조 불확실 상태에서는 주문하지 않는다.
7. 이전 연결의 늦은 종료 이벤트·중복 재접속·파싱 실패가 새 연결을 잘못 종료하지 않는다.
8. 단절 중 부분체결·취소 지연·청산 응답 유실에서 중복 주문이나 보유량 초과 매도를 만들지 않는다.
9. 가상 비교는 관측 불가능한 공백을 수익성 있는 체결로 만들어내지 않는다.

운영 검증:

- 저장된 시세와 연결 장애 주입을 이용해 전후 대기 시간을 비교한다. 실시간 가격 변화와 복구 효과를 혼동하지 않는다.
- 실제 주문을 끈 별도 시험 환경에서 연결 복구·DB 복원을 확인한다. 동일 계좌로 두 주문 실행기를 동시에 돌리지 않는다.
- 모의 서버에서 보유·미체결 0 확인 후 배포하고, 장중 최신 시세·상태 사유·원장 기록을 점검한다.
- 정상 데이터의 짧은 단절을 이유로 무조건 30분 대기하는 경우가 없어야 한다. 긴 실제 공백에 따른 차단은 남아 있어야 한다.
- 반복 초기화 원인이 로그로 구분되고, 관측되지 않은 시세 보충 및 중복 주문이 없어야 완료로 판단한다. 수익 증가나 매매 횟수 증가는 완료 기준으로 삼지 않는다.

## 7. 작업 순서와 배포

1. SSH 접근 복구 또는 서버 자료 확보 → 장애·거래 기록 확인.
2. 공통 데이터 품질 판정, 진단 이벤트, 상태 표시 구현.
3. 시세 보존·SQLite 복원·연결 세대 및 재접속 제어 구현.
4. 회귀 테스트·장애 주입·조회 전용 시험.
5. 코드 이미지·원장 백업, 보유·미체결 대조 후 단일 실행기로 배포.
6. 실제 장중 검증 결과를 개선 전후 비교 기록에 남김.

복구 불가 오류, 주문 중복 위험, 계좌 대조 불일치가 생기면 신규 진입을 막고 원장을 보존한다. 롤백은 주문 결과 대조 후 기존 이미지로 수행하며 오래된 DB 백업으로 거래 이력을 덮어쓰지 않는다.

기존 실험 종료일 2026-09-25는 유지한다. 개선 전후 기간과 버전을 분리하고, 데이터 품질 때문에 제외된 시간을 보고한다. 짧은 표본으로 수익성을 확정하거나 실전 전환을 결정하지 않는다.
