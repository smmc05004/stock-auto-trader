# 작업 흐름 및 Docker 이미지 배포 규약

작성일: 2026-09-16. 이 문서는 앞으로 적용할 작업 규칙과 승인된 배포 설계를 기록한다. 실제 구현 완료 여부는 아래 상태 표와 코드·인프라 증거를 함께 확인한다.

## 현재 상태와 목표

| 항목 | 구현 브랜치 상태 | 실환경 확인 |
|---|---|---|
| 개발 흐름 | 작업 브랜치·커밋·PR 규약 및 AI 진입 문서 | main 보호 적용: PR 필수, verify·image 필수, 관리자 포함 |
| CI 및 이미지 | 검사 후 Linux amd64 이미지 빌드·격리 smoke 검사 | PR CI 결과로 확인 |
| 발행·배포 요청 | 검사한 이미지를 artifact로 전달, ECR digest 발행, SSM 호출 | AWS 권한/변수 설정 및 활성화 필요 |
| AWS 설치 | `deploy/image/infrastructure.json` ECR·OIDC·IAM·SSM 템플릿 | 실제 스택 생성 미실행 |
| 주문 중 교체 | 파일 기반 신규 매수 허가·최신 계좌 대조·단일 실행기 교체 | 자동 테스트 완료, EC2 인수 미실행 |
| 부팅·복구 | 목표 버전 확인 타이머·부팅별 허가·실패 릴리스 차단 | 서버 최초 설치 미실행 |
| 이미지 롤백 | 주문 허가 전 실패한 후보의 직전 호환 이미지 복구 | 자동 테스트 완료, 최초 배포는 이전 ECR 버전 없음 |

상세 설치·활성화·제한은 [EC2 이미지 자동 배포 운영](image-deployment-operations.md)을 읽는다. `PAPER_IMAGE_CD_ENABLED=true` 설정 전에는 기존 서버에 적용되지 않는다. 과거 수동 배포 기록은 `git-deployment-process.md` 등에서 확인하되 새 표준과 혼동하지 않는다.

## 1. 개발과 PR

1. 현재 작업 트리와 브랜치·PR 상태를 확인한다. 새 작업은 최신 main을 기준으로 작업 브랜치를 만든다. 기존 변경이 있으면 보존하고 소유 작업을 먼저 확인한다.
2. 기능·수정·문서를 브랜치에서 작업한다. 변경 목적과 관계없는 파일을 함께 커밋하지 않는다.
3. 현재 CI 기준 `npm test`, `npm run lint`, `npm run build:paper`, `npm run build`를 통과시킨다. 문서만 바꾸면 링크·diff를 점검하고 불필요한 실행 테스트를 추가하지 않는다. PR의 필수 CI 자체는 우회하지 않는다.
4. 커밋하고 PR에 문제, 결과, 검증, 운영 영향을 적는다. 필요한 범위의 사용자 승인과 저장소 정책을 충족한 뒤 머지한다.
5. 배포 시작점은 `push`의 main 커밋으로 한다. PR 워크플로에는 배포 권한을 부여하지 않는다. main 보호 기능의 지원 여부와 실제 적용 여부도 확인한다.

문서 작성·계획 수립만 요청받은 경우에는 그 범위를 지킨다. 작업 완료 보고에서 원격 반영이나 머지가 남아 있으면 명시한다.

## 2. 이미지 빌드와 발행

`main → CI 통과 → Docker 이미지 빌드·검증 → ECR 발행 → 배포 목표 등록 → EC2 적용·검증` 순서다.

- EC2와 같은 `linux/amd64`, 현재 런타임과 같은 Node 22를 사용한다.
- 전체 Git SHA를 이미지 태그와 OCI revision에 기록한다. 실제 실행 참조는 `repository@sha256:...`로 고정한다. `latest`나 재지정 가능한 태그만으로 배포하지 않는다.
- Node·SQLite 실행과 데이터 디렉터리 권한 등 이미지 자체 검사를 주문 없는 격리 환경에서 수행한다. 검증한 이미지와 발행·배포하는 이미지는 동일해야 한다.
- 운영 Compose는 `build:` 없이 이미지를 참조한다. EC2는 애플리케이션 소스를 받거나 npm 설치·빌드를 수행하지 않는다.
- 비밀정보는 이미지·빌드 인자·캐시에 넣지 않는다. 서버 환경설정은 유지하고 이미지 빌드와 분리한다.
- 이미지 보관 정책은 현재 실행본·직전 정상본·배포 대기본을 보호한다. ECR 저장량과 Actions 사용량을 확인하며 무료라고 단정하지 않는다.

## 3. 연결과 배포 목표 저장

- 서울 리전의 ECR과 기존 EC2를 사용한다. EC2 인스턴스 ID를 기준으로 Systems Manager에 명령을 전달해 공인 IP 변경에 의존하지 않는다.
- GitHub Actions는 OIDC로 임시 AWS 권한을 얻는다. 신뢰 조건은 실제 저장소의 OIDC subject 형식과 main 브랜치에 제한한다. GitHub Environment를 사용한다면 subject 및 브랜치 제한도 그에 맞게 검증한다.
- EC2 역할에는 이미지 읽기, 해당 Parameter Store 경로 및 SSM 운영에 필요한 권한만 부여한다. SSM Agent, 외부 통신, 인스턴스 역할 연결은 최초 설치 때 확인한다.
- Parameter Store에는 목표 커밋·digest·릴리스 식별자를 저장한다. 서버 상태 기록에는 목표 버전과 실제 적용 버전, 시각, 실패·보류 사유를 구분한다.
- 최초 서버 준비용 Compose·systemd·배포 제어 스크립트는 버전 관리된 설치 절차로 적용한다. 이후 이 제어 파일의 변경 역시 PR과 버전이 있는 배포 묶음으로 관리하며 애플리케이션 소스 수동 복사로 돌아가지 않는다.

## 4. 거래 중 교체 절차

1. 배포 잠금을 획득하고 목표 릴리스가 아직 유효한지 확인한다. 이미 적용된 digest면 변경하지 않는다.
2. 새 이미지를 미리 내려받는다. 다운로드 실패는 현재 실행기에 영향을 주지 않는다.
3. 영속적인 배포 준비 상태를 설정해 신규 매수만 중지한다. 시세 연결·미체결 취소·기존 전략의 청산·계좌 대조는 계속한다.
4. 증권사 조회가 최신이며 보유·미체결이 모두 0인지 확인한다. 배포 때문에 강제 청산하지 않는다. 제한 시간 내 확인되지 않으면 교체를 보류하고 기존 실행기를 유지한다. 배포 준비 상태 해제 여부와 이유를 기록하며 무조건 주문을 재개하지 않는다.
5. 일관된 SQLite 백업을 만들고 기존 실행기를 정상 종료한다. 강제 종료를 정상 배포 절차로 사용하지 않는다.
6. 동일한 환경설정·실제 데이터 볼륨으로 새 컨테이너를 시작한다. Compose 프로젝트명 및 볼륨명을 고정해 디렉터리 변경으로 새 빈 DB가 생성되지 않게 한다. 초기 설치 때 기존 볼륨의 실제 이름을 확인한다.
7. 커밋·digest·DB 열기·단일 실행기·계좌 대조를 확인한 후 주문 허용 상태를 복원한다. 거래 시간 외 검증과 장중 시세 검증을 구분한다.

프로세스 생존, 배포 준비 완료, 전략의 데이터 준비 완료는 별도 상태다. `/health`만으로 배포 성공을 선언하지 않으며 30분 관측 대기를 배포 실패와 혼동하지 않는다.

## 5. 서버 중지·동시 머지·실패

- **서버 중지:** 이미지는 발행하고 목표 버전을 저장하되 EC2 적용은 대기로 기록한다. 배포를 위해 임의로 서버를 켜지 않는다. 다음 부팅과 주기적인 목표 버전 확인에서 재시도한다.
- **부팅:** 기존 Docker 자동 재시작이 검증 전에 주문을 시작하지 못하도록 systemd와 재시작 정책을 함께 수정한다. 최신 목표 확인 실패나 계좌 상태 불명확 시 신규 주문을 차단하고 복구·대조를 우선한다.
- **연속 머지:** GitHub 배포 작업과 서버 작업을 직렬화한다. 진행 중 배포를 강제 취소하지 않는다. 오래된 작업이 더 최신 목표를 덮어쓰지 않도록 발행·적용 직전에 릴리스 순서와 main 상태를 검사한다.
- **교체 직후 실패:** 신규 주문이 없고 DB가 이전 이미지와 호환될 때 직전 정상 이미지로 복구한다. 신규 주문 발생·상태 불명확·비호환 DB 변경이면 자동 롤백을 멈추고 대조·복구한다.
- **원장 보존:** 코드 롤백과 DB 복구를 구분한다. 백업 DB 덮어쓰기로 이후 거래 기록을 삭제하지 않는다. 마이그레이션은 호환성 및 실패 복구 방법을 사전 명시한다.
- **결과 표시:** `image_published`, `pending`, `deploying`, `deployed`, `failed`, `rolled_back`을 구분한다. 이미지 업로드 성공을 EC2 배포 성공으로 보고하지 않는다.

## 6. 구현 순서와 인수 기준

| PR | 구현 범위 | 확인할 결과 |
|---|---|---|
| 1 | CI, 이미지 검증·발행, ECR·OIDC 설정 | main SHA에 대응하는 검증된 이미지, PR에서 배포 권한 사용 불가 |
| 2 | 배포 준비 프로토콜, 원장 보존, 상태 검증·복구 | 주문 중 안전한 교체·보류, 두 실행기 중복 주문 차단 |
| 3 | SSM 배포 연결, 목표 버전 저장, 부팅 적용, 상태 기록 | main 머지 후 자동 적용 및 서버 중지·재시작 시 후속 적용 |

원래 위 세 단계의 PR을 계획했다. 이번 구현은 안전 기능과 배포 연결이 함께 검토되도록 하나의 기능 PR에 묶고, 실제 활성화는 기본 비활성 변수로 분리한다. 테스트와 AWS/서버 최초 설정이 완료되기 전에 자동 교체를 활성화하지 않는다.

최종 인수 시 정상 배포, CI 실패 시 차단, 서버 중지 중 머지, IP 변경, 연속 머지, 다운로드 실패, 계좌 조회 실패, 교체 직후 오류, 기존 DB 보존을 확인한다. 검증은 모의투자 범위에서 수행한다.

## 문서 유지

- 새 세션의 진입점은 루트 `AGENTS.md`다. `CLAUDE.md`는 같은 규약을 가져온다. README에도 진입 링크를 둔다.
- 동작을 바꾸는 PR은 이 문서의 상태 표와 운영 절차를 함께 갱신한다. 증거 없이 완료로 바꾸지 않는다.
- 문서 자동 로딩을 지원하지 않는 AI 도구에서는 사용자가 `AGENTS.md를 읽고 시작해`라고 지정해야 한다. 저장소 밖에서 시작하거나 해당 파일이 없는 브랜치를 여는 경우 자동 인지를 보장할 수 없다.
